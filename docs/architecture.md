# 架构说明

一份给自己看的实现笔记：为什么这么拆、状态存在哪、换班怎么保证不重复操作。

## 进程模型

单进程，三个线程：

```
uvicorn (asyncio)
 ├── FastAPI 路由          → 同步端点丢到线程池，不阻塞事件循环
 └── scheduler 线程 (daemon)
       ├─ 每 N 秒（对齐到设置的起始秒位）：engine.reconcile_all()
       ├─ 每分钟：检查日报时间
       └─ 每小时：清理事件与采样
```

没有独立 Worker、没有任务队列。对账是幂等的，重复执行没有副作用，所以不需要租约或分布式锁 —— 一个进程内用 `threading.Lock`（非阻塞）挡住并发即可。

SQLite 用 WAL + 每线程独立连接（`threading.local`）。读写混跑不打架；`busy_timeout=15s` 兜住偶发争用。

## 数据模型

```
servers ──────────── 一台机器 = 一个阿里云账号 + 一个 ECS 实例
   │                  quota_gb / threshold_gb / 运行时快照（流量、状态、IP）
   │
   ├── keepalives ─── 单机保活（server_id 唯一）
   │
   └── shift_members ─┐
                      ├── shift_groups ── 联合换班组
                      │      anchor_at：轮换周期的时间原点
                      └── position / hours：顺序与时长

shift_runs ──────── 每个「班次」的执行状态
                      slot = 该班次的开始时间戳（Unix 秒）
                      phase = pending | switching | settled | failover | breaker | limit_stop | error

flags ───────────── 一次性标记（通知去重、恢复待确认）
events ──────────── 事件流，给人看的
traffic_samples ─── 流量采样，给图表用
```

关键设计：**`slot` 用「班次开始时间戳」而非「日期 + AM/PM」**。

这样无论是 2 台各 12 小时、3 台各 8 小时，还是 10h + 14h，都能天然得到唯一且稳定的 slot key。改成员或改时长时重置 `anchor_at`，slot 自然翻新，不会沿用旧标记。

## 轮换算法

```python
total  = Σ(member.hours) * 3600
elapsed = max(0, now - anchor)
cycle  = elapsed // total          # 第几个周期
offset = elapsed % total           # 周期内偏移
逐成员累加，第一个满足 offset < Σhours 的就是当班
```

O(n) 且无状态。`anchor_at` 是唯一需要持久化的东西 —— 手动换班就是改它。

手动换班为什么是「平移 anchor」而不是「记一个强制下次当班」？因为后者会引入一个额外的状态机分支（要判断什么时候失效、跟自然轮换怎么合并）。平移 anchor 之后，系统仍然只有一个真相来源（时间 + anchor），逻辑不分叉。

平移量 = `now - 下一个成员在本周期内的累计起点`。等价于「把 now 当成下一班的第 0 秒」。

## 对账流程

`reconcile_group` 一次跑完：

```
1. 算当班 / 待机
2. 并行刷新所有成员的流量与实例状态
3. 当班超阈值？
   ├─ 有没超的成员 → 换人（failover=true），原当班转入待机集合
   ├─ 全都超了     → 熔断：全员 StopCharging，确认后推熔断报告
   ├─ 别人查不到   → 保守维持（不能因为 API 抖动就把机器停掉）
   └─ 关闭了故障转移 → 超限停机兜底
4. 当班没 Running → Start（若该班次已结算过，打上「待恢复」标记）
5. 当班 Running   → 其余全部 StopCharging
6. 全部就绪（当班 Running + 其余 Stopped/StopCharging + 有公网 IP）
     → 同步 DDNS → 推「换班完成 / 临时换班」
7. 未就绪 → 检查是否超过 10 分钟 → 推「换班异常」
```

几个刻意的选择：

- **DDNS 必须先于通知**。通知文案里会回显 `☁️ DDNS：✅ 已同步`，先发通知再同步会撒谎。
- **只在关键时刻查 Cloudflare**。巡检（`dns.reconcile`）只比本地 `last_ip`，一个请求都不发；手动开机、单机保活拉起、换班首次结算传 `verify=True`，先读 CF 上的实际记录，一致就跳过 PUT。`dns_records.last_at` 的语义是「上次真正改写记录的时间」，核对发现没变时不刷新，界面上不会出现假的「刚刚」。
- **待机没确认停机就不算结算**。只下发了 Stop 指令不算，得看到 `Stopped` 才算 ready，否则会误报「换班完成」。
- **别人的状态查不到时不动手**。宁可这轮什么都不做，也不要基于空数据把实例停掉。
- **超限兜底与熔断分开**。熔断是「都没得选」，超限停机是「换不了但还在跑」；两者的通知文案不同，用户要知道是哪一种。

### 换班加速（不影响巡检周期）

一轮换班要跨三步动作（开当班 → 停待机 → 结算），每步都得先读到上一台状态到位。
如果全压在巡检间隔上，4 分钟的换班里真正干活的只有十几秒，剩下全在等下一个闹钟。

做法是**两条互不干扰的通道**：

| 通道 | 频率 | 查谁 | 查什么 |
|---|---|---|---|
| 日常巡检 `reconcile_all` | 严格按设置里的巡检间隔，**没有任何临时提速** | 全部实例 | 状态 + 流量 |
| 换班加速 `reconcile_awaiting` | 10 秒 | 只查「刚下发过指令」的组 | **只查状态，不查流量** |

- **窗口是「下发指令之后」**，不是整段换班期。当班已经在跑、待机还没下停机指令时
  不加速；全部到位（ready）立刻关闭。
- **窗口有三重刹车**，缺一个 10 秒轮询就会变成常态：单窗口最长 5 分钟（到点回落）、
  重复登记不续期、**同一班次累计加速不超过 10 分钟**（预算用尽就不再打开窗口，
  只有换了班次才重置）。卡死场景（竞价没库存、欠费冻结）里每轮巡检都会重发指令，
  光靠单窗口 TTL 挡不住窗口被一次次打开 —— 3 台组那样会变成每天约 2.6 万次
  `DescribeInstances`。
- **按组互斥**。两条通道都可能跑同一组，用按组的锁隔开：抢不到就跳过这一组，
  不会出现两路都读到「当班没起来」、各发一次开机。锁是按组的，所以日常巡检
  只会跳过被加速推进的那一组，保活、闲散、其他组照常跑。**用户入口也要拿这把锁**：
  新建组 / 手动换班 / 解散 / 单机手动开关机都会先收掉加速窗口再排队进锁，
  否则「解散不下发任何指令」和「手动点一下就生效」这两句承诺都会被并行的加速轮推翻。
- **开机、停机指令各 60 秒内不重发**（只在加速轮生效）。否则 10 秒一轮就是每 10 秒
  砸一次 `StartInstance` / `StopInstance`；日常巡检读的是真实状态，读到 `Stopped` /
  `Running` 就该重试，不受这条限制。
- **「当班起不来」判死 = 次数 + 墙钟双条件**（**仅加速轮**）：`tries >= 3` 且距第一次
  发现没在跑已过 180 秒。加速后次数涨得快，只看次数会在 30 秒内误判、连环换人；
  日常轮仍按次数判，把巡检间隔调到 30 秒的用户换人时机和以前完全一致。
- **加速轮不写健康事件**。状态巡检的失败计数、升红阈值、事件里那句「每 N 秒重试」，
  都是按用户配的巡检间隔算的；10 秒一轮照写的话，一次 30 秒抖动就会把事件刷成
  `error`，文案里的重试频率也和实际对不上。状态读不到时**立即关窗口**回落巡检节奏 ——
  读不到就说明「等状态到位」这个前提已经不成立了。
- **不查流量**，但**每两个巡检周期补读一次**：加速轮沿用库里上一轮读数（最多旧一个
  巡检周期）。流量是 GB 级慢数据，不影响超限判断；而 CDT 是账号级接口、一台一次，
  跟着 10 秒一轮纯属白烧。日常巡检因抢不到组锁而跳过的那几轮，靠这次补读兜住。

## 事件标题规范

事件标题统一由 `messages.ev(结论, 对象)` 拼：**结论在前，对象进末尾的括号**，与通知标题
`CDT {结论}报告（{范围}：{对象}）` 同构。结论里不重复对象名，也不再用「对象：结论」或
「对象 结论」的写法 —— 别名长短不一时，两种写法会让整列文字对不齐。

| 对象 | 写法 | 例子 |
| --- | --- | --- |
| 单台服务器 | 裸别名 | `单机保活抢占恢复（AliYun-CDT）` |
| 整个换班组 | `换班组：组名` | `换班完成（换班组：香港）` |
| 组内当班 | `换班组：组名，当班 别名` | `当班未就绪（换班组：香港，当班 A）` |
| 组内普通成员 | `换班组：组名，成员 别名` | `状态巡检异常（换班组：香港，成员 B）` |
| DNS 记录 / 系统 | 域名 / `系统` | `DNS 记录已更新（a.example.com）`、`配置已更新（系统）` |

几个约束：

- **括号只有一层**。原因写进结论（`当班未就绪，故障转移（换班组：香港）`），不套第二个括号；
  结论里**最多一个逗号**（原因，结果），三段以上就该拆到概览里。
- **服务器不加类型前缀**，事件列表里九成是机器；换班组一律带前缀，避免与同名实例混淆。
- **结论用词固定**：单机保活分两条渠道，各说各的 —— 窗口到点开/关走
  `单机保活窗口暂停 / 单机保活窗口恢复`，其余拉起（掉线被抢占、手动关机后重新开保活、
  刚加进保活）走 `单机保活抢占恢复`；流量超限暂停仍叫 `单机保活暂停`。
  巡检系列只有「状态巡检异常 / 状态巡检已恢复」两句，具体归属交给括号里的对象；
  费用系列同构：「费用查询异常 / 费用查询已恢复」，一轮巡检一次、一轮费用一次，
  两者互不混用（60 秒一轮叫**巡检**，10 分钟一轮叫**查询**）。
- **进行中用「X 中」，完成用「已 X」**：`换班进行中 → 换班完成`、`当班自动拉起中 → 当班已恢复运行`、
  `单机保活抢占恢复中 → 单机保活抢占恢复`、`单机保活窗口恢复中 → 单机保活窗口恢复`。
  同一个动作全程只有一个名字，收尾只换时态。
- **不加修饰副词**：`已节省停机` 不写 `已强制节省停机`，`当班未就绪` 不写 `疑被抢占` ——
  判断依据放详情里，标题只留事实。
- **` / ` 只表示「结论 / 细节」**。`已保存 / 时区、流量阈值`、`等待停机到位 / 已用 30.00 GB（阈值 100 GB）`
  是标准用法；同类字段并列（`当班 A，待机 2 台，DDNS 已同步`）一律用逗号，别再借 ` / ` 当分隔符。
- **只有「持续时间」的事件在概览里带 `HH:MM:SS`**：巡检异常、费用查询异常、保活重试这类会跨多轮
  的事件，首句写「19:10 巡检失败：…；每 60 秒重试，恢复后自动更新」；DNS、配置、站点纠正这类
  一步就完的不带 —— 列表本身已经显示时间，重复一遍只占宽度。
- **一次连续故障只有一条事件**：网络抖动、缺权限这类会连续多轮失败的原因，首轮建 `status="running"`
  事件并挂 `pending_kind`，后续轮次只覆盖概览（`19:26 仍失败（连续 3 次）：…`）并在里程碑
  （第 2/5/10/30/60 次）补一行进度，恢复时找到它收尾。绝不能每轮失败新开一条 ——
  否则时间线会被「失败 / 已恢复」成对刷屏，还看不出是一段故障。计数与起始时刻存在
  `flags`（`read_err:{id}` / `billing_err:{id}`），恢复时据此写「连续失败 N 次，持续约 M 分钟」。
  新建事件前先清残留计数，避免出现「第 1 次失败」配「连续失败 14 次」。
- **`kind` 决定图标形状，`level` 决定颜色**：同为「读不到数据」的巡检与费用都用 `kind="warning"`（三角），
  巡检连错 3 次升 `level="error"`（红，状态读不到会影响保活判断），费用恒 `warning`（橙，只影响展示）。
- **恢复统一叫「已恢复」**：标题 `状态巡检已恢复`、概览 `19:32 已恢复（此前连续失败 4 次，持续约 22 分钟）`、
  过程条目 `19:32 已恢复`。同一件事三个位置只换信息量，不换词。
- **概览只陈述，不劝人**：检查项、操作建议放过程条目（`排查建议：检查记录名、Token 与 Zone`），
  `等待 5 分钟仍未同步（…），请检查…` 这种祈使句不进摘要。

## 事件三要素

一条事件要能被「扫一眼」和「点开看」两种读法都读懂，三段各管一件事：

| 位置 | 写什么 | 反例 |
| --- | --- | --- |
| 标题 | 结论 + 对象；进行中写 `X 中`，收尾换成 `已 X` | 收尾了还写「拉起完成」 |
| 概览（detail） | **进行中**只写「在等什么」：`等待停机到位（节省停机）`；**完成**只写结果，最多补一段原因，用「 / 」分隔：`已停止（节省停机） / 已用 199.00 GB` | 只写「已下发停机指令」——指令下发≠做到；或者写「A → B」这种看不懂的状态迁移 |
| 详情（progress） | 完整过程 + 结果：为什么做、下发什么、确认到什么状态、DDNS、通知 | 只有第一步，后面什么都没有 |

**凡是要等外部状态的动作，事件一律先 running，等确认到位才收尾**：手动开关机、
单机保活拉起 / 窗口暂停、超限停机、换班结算都走这条路（`pending_status` + `pending_kind`，
由确认器每 5 秒轮询）。只有「指令下发成功」这一件事可写的，不许直接标完成。

## 幂等与去重

每次要发通知前，先查 `flags`：

| 标记 | 作用 |
| --- | --- |
| `notify:{group}:{slot}:settled` | 同一个班次只推一次换班报告 |
| `notify:{group}:{slot}:failover` | 同一个班次只推一次临时换班报告（与上面分开，否则「先结算后又转移」会被吞掉） |
| `breaker:{group}:{slot}` | 熔断只报一次；流量回落、当班恢复运行后清掉 |
| `limit_stop:{group}:{slot}` | 超限停机只报一次；同上，回到正常路径就清 |
| `timeout:{group}:{slot}` | 换班异常只报一次 |
| `recovery:{group}:{slot}` | 待确认的抢占恢复 |
| `start_err` / `stop_err` / `member_err` / `keepalive_err` | 同类失败只记一条事件，恢复后自动解除，避免每分钟刷屏 |
| `keepalive_rest:{server_id}` | 已记过「单机保活窗口暂停」，休止时段内不再重复记 |
| `keepalive_rest_fail:{server_id}` | 休止时段停机失败只记一次，下一轮继续重试但不刷屏 |

标记落库而不是内存，容器重启后不会重复推送。

开关机的去重靠状态判断而不是标记：`status != Running` 才 Start，`status != Stopped` 才 Stop。阿里云那边状态是真相，所以不需要额外记「已经发过启动指令」。处于 `Starting/Stopping` 这类过渡态时不下发新指令，只等它落地。

### 故障转移是「粘住」的

一个班次内一旦因流量超限切到替补，本班次剩下的时间就固定在替补上（`shift_runs.failover` + `duty_server_id`）。不这么做的话，每轮对账都会重新按时间推导出原当班、再判定一次超限，结果是每分钟换一次机器、事件刷屏、通知重复。界面上的「当班」高亮也跟着 `run.duty_server_id` 走。

### 保留期

| 表 | 保留 | 原因 |
| --- | --- | --- |
| `events` | 14 天（可配） | 只是给人看的流水 |
| `flags` | 90 天起 | 里面混着「已让位」「已熔断」这类长期状态，不能跟事件一起删 |
| `shift_runs` | 30 天 | 抢占恢复要靠上一轮 `phase` 判断，班次最长可到 7 天，删早了会重复推「换班完成」 |
| `traffic_samples` | 7 天 | 画曲线用 |

## 单机保活与换班的互斥

同一台机器如果同时挂在两个模块下，会互相拉扯：保活看到 Stopped 就拉起来，换班看到不该它当班就停掉，来回震荡。

处理方式：`reconcile_all` 先算出「所有进组的 server_id」（`_grouped_server_ids()`，换班组和启用中的均衡组都算），保活对账时跳过这些机器，并记一条一次性警告。**让位给换班和均衡**，因为它们的约束更强（同一时刻只有一台该接流量）。漏掉均衡组的话，休息中的成员会被保活按「闲散手动」判断，超限时推一条「超限停机（闲散手动）」，范围写错、还会把用户的机器停掉。

判定收在 `app/owners.py`：`managed_map()` 给出每台机器归谁，`ensure_free()` 在三个模块入组时统一校验。单机保活 / 联合换班 / 流量均衡三者互斥，一台只能占一个。

## 流量均衡

不看时钟，看累计流量：域名始终指向「用得最少」的那台，适合包年包月、不缺机器只缺额度的场景。

### 与联合换班的分工

| | 联合换班 | 流量均衡 |
| --- | --- | --- |
| 选人依据 | 排班表（时刻 / 天数） | 累计流量最少 |
| 切换动作 | 开新当班 → 确认 Running → 改 DNS → 停旧当班 | 同上，但「停旧」由成员的下班动作决定 |
| 成员常态 | 只有当班在线 | 多数保持在线（停机不省钱） |
| 适用 | 抢占式，省实例费 | 包年包月，摊 CDT 额度 |

### 评估与切换

每轮对账只读当班一台；到 `next_eval_at` 才读全员，比较 `当班累计 − 最少成员累计 ≥ diff_gb`，同时要求距上次切换已过 `min_duty_minutes`。两个条件都满足才切，否则把评估点后移到下一个周期。参数：周期 1/3/6/12/24 小时，差值 10/30/50 GB。

最短当班（`min_duty_minutes`，默认 30 分钟）不再做成可填的数字：均衡判断的是**累计流量**，而评估点最密也是 1 小时一格，30 分钟的冷却永远先到点，填多少都不影响结果 —— 与其放一个看起来能调、实际不起作用的输入框，不如固定成默认值。字段与判定都留在引擎里，未来若支持更密的评估周期可直接复用。

评估点按**整点网格**排（`balance._next_slot`）：以组时区的本地 0 点为原点，1 小时=每个整点、3 小时=00/03/06…、24 小时=每天 0 点。不是「上次时间 + 周期」——那样 13:47 建的组以后永远在 47 分评估，日志里全是零碎时间，也没法和整点巡检对表。首次指派和每次切换结算都会重排到下一个整点。

切换是跨轮次的状态机（`balance_state.phase`）：

```
idle → starting（已下发开机、等 Running）
     → settle（改 DNS → 按 off_action 处理上一台 → 回 idle）
起不来     → attempts ≥ 3 且已等满 180 秒，或超过 10 分钟 → 换下一个候选人
没人可接   → exhausted（能读到的都到阈值：整组停机 + 熔断通知），每小时复查
读不到流量 → 不动，排到下一个评估点（不把「没数据」当「用完了」）
推不下去   → 收尾事件、phase 拨回 idle、当班退回原来那台
```

每轮 `_reconcile` 的判断顺序就是优先级，**流量保护在最前面**：

1. **当班到阈值** → 关着故障转移就只停当班（`balance_limit`），开着就立刻换人，都不等评估点；
2. **当班没在跑** → 原位拉起（`balance_recover`），不再等下一个评估点（24 小时周期的组会空一整天）；
3. **到评估点** → 读全员，休息成员超限照样停机，再比差值决定切不切。

「读不到流量」和「全员到阈值」必须分开判（`_candidate_status`）：前者只是没数据，不动；后者才熔断。混在一起的后果是 CDT 抖一下就把整组停机，还推一条「全员到阈值」。

### 加速通道

巡检间隔来自用户设置（默认 60 秒，可到几十分钟），而「下发开机 → 等 Running」是秒级的事。`scheduler._balance_loop` 每 10 秒（`CDT_BALANCE_AWAIT_INTERVAL`）调一次 `balance.reconcile_awaiting()`：只挑 `phase in (starting, switching)` 的组（`repo.balance_awaiting_ids()`），走同一段 `_reconcile(fast=True)` —— **只读状态、不查流量**，CDT 是慢数据，差十几秒不影响超限判断。与换班的 `_shift_loop` 同构，日常巡检间隔一秒不改。

判死必须「次数 + 墙钟」两个条件：加速轮 10 秒一次，只看次数的 3 次就是 30 秒，一次状态同步稍慢就把慢启动判成起不来，触发连环换人。下发开机按 `DUTY_START_RETRY_SECONDS`（60 秒）节流，失败下一轮再试（开机接口是幂等的）。

### 三个容易踩的点

1. **一个账号一台。** `aliyun.get_traffic_gb()` 取的是 AccessKey 所属**账号**的月度出向流量，同账号放两台会读到同一个数字，评不出高低。界面上直接写了这条提示。
2. **跨月不清当班。** 1 号 0 点全员归零，此时按规则容易立刻乱切一轮，所以跨月那一轮只重置 `cycle_key` 与 `slot_base_gb`，当班不动。
3. **停机成员照样参与评选。** 它只是流量冻结，不是归零；被选中时先开机、确认 Running 再改 DNS，不会把域名指到停着的机器上。

### 与 DNS 的关系

`dns.TARGET_BALANCE` 是第四种绑定目标。均衡组切换期间，DNS 巡检让位（`_shift_events` 会把这个组的 `balance_switch` 事件一并算进去），避免巡检抢在结算之前改解析、把「旧 IP → 新 IP」这句话洗掉。

### 事件与通知

结算按原因分三条，和换班的「换班完成 / 手动换班完成 / 故障转移」一一对应；另有四种非常规收尾：

| 场景 | 事件 kind / 标题 | 通知 | 开关 |
| --- | --- | --- | --- |
| 新建组后的首次指派 | `balance_new` / 新建均衡组 | 不发（用户刚点完保存） | — |
| 巡检里补做首次指派、差值到点 | `balance_done` / 均衡完成 | `CDT 均衡完成报告` | `notify_on_balance` |
| 用户点立即均衡 | `balance_manual` / 手动均衡完成 | `CDT 手动均衡完成报告` | `notify_on_balance` |
| 当班到阈值、起不来换人 | `balance_failover` / 当班超限，故障转移（起不来写当班未就绪） | `CDT 故障转移报告` | `notify_on_failover` |
| 当班掉线被原位拉起 | `balance_recover` / 当班已恢复运行 | `CDT 抢占恢复报告` | `notify_on_recovery` |
| 当班或休息成员到阈值停机 | `balance_limit` / 流量超限，已节省停机 | `CDT 超限停机报告` | `notify_on_limit_stop` |
| 没人能接班（能读到的都到阈值） | `balance_breaker` / 全局熔断 | `CDT 全局熔断报告` | `notify_on_breaker` |
| 切换超过 10 分钟没到位 | `balance_error` / 均衡异常 | `CDT 均衡异常报告` | `notify_on_balance_error` |

新建组和掉线恢复都不推「均衡」报告：前者是用户自己刚做过的事，后者是系统把班补回来（事件里能查到全过程，真起不来会走「故障转移」，那条才推送）。恢复本身仍会提醒一次「抢占恢复」，开关是 `notify_on_recovery`。「新建均衡组」这条事件从头到尾不改名 —— 和「新建换班组」同一套口径。

事件概览与换班结算同格式（`当班 X，待机 N 台，DDNS 状态`），「为什么切」和通知结果写进详情进度。故障转移单独挂 `notify_on_failover`：关掉「流量均衡完成」不该把故障转移一起静音。

通知正文**以 v1.6.8 的换班报告为基准，只多一行流量**：块仍是 `running_block` / `stopped_block`，字段和顺序不动。均衡报告用同一对块，**只有标题（均衡组）和概览那行不同**：均衡完成 = 一块 `当班账号` + 每台 `待机账号`；故障转移 = `当班账号` + `超限账号`（起不来时写 `离线账号`）+ 其余 `待机账号`。台账用角色而不是运行/停止 —— 均衡组的待机成员可以设「下班后保持运行」，真在跑的那台写成「停止账号」会和状态行打架。

图标只说一件事：`🟢` 留给当班那台，非当班成员在跑用 `🔵`（在跑，但不在这一班），停着用 `⚪`。状态文字仍是回读的真实值（`Running` / `Stopped (StopCharging)`）：蓝球不改状态含义，只让「谁在承载流量」不看标签也能认出来。换班组的待机块没有「保持运行」这个选项，仍是 `⚪ 停止账号`。

每块在状态行上面带一行 `📈 流量：x GB`（只写已用量，不带套餐额度），收报告的人据此能直接看出整组流量分布和下一次会切给谁。这一行同时取代了旧版只有超限账号才有的 `📈 已用：x GB`，位置没变；额度、剩余和使用率在每日报告里看。抢占恢复只列一台，用的是同一行、同一个位置（地域之后、状态之前），三种范围（单机保活 / 换班组 / 均衡组）一致。

这行只留一个数，**不写配额也不写阈值**：报告一行一台已经够长，配额是每台自己的套餐数，对「谁快超限、下一次切给谁」没有增量信息；阈值是组里调出来的判据，「为什么切」靠正文那句原因和事件详情说清，不在每个账号块里重复。只有超限停机 / 全局熔断这类「已经超了」的报告才写成 `📈 已用：x GB（阈值 y GB）` —— 那里没有阈值就读不懂「190 GB 为什么算超」。

### 运行窗口（单机保活）

`keepalives` 上有两组可选字段，都为空表示不限（等于没有这个功能）：

| 字段 | 约束 | 判定 |
| --- | --- | --- |
| `start_time` / `end_time` | 24 小时循环：`end > start` 当天内；`end < start` 跨天到次日（`20:00–06:00`）；`end=00:00` 且 start 非零表示到 24:00；`end == start` 等于不限 | 当天内 `start ≤ 现在 < end`；跨天 `现在 ≥ start` 或 `现在 < end` |
| `start_day` / `end_day` | 同一个月内，`1 ≤ start ≤ end ≤ 31`，不跨月 | 按当月天数截断后比较 |

两项同时填是**交集**。窗口外：主动按实例的停机模式停机，落一条「单机保活窗口暂停」——**下发指令之后事件仍是进行中**，要等确认器看到 `Stopped` 才收尾（概览写「已暂停（节省停机）」），全程不发通知；回到窗口内：落一条「单机保活窗口恢复中」并在同一轮下发开机，那条事件挂 `pending_kind=keepalive` 等确认，但 `kind=keepalive_quiet`，确认器据此不发「抢占恢复」。

确认器（5 秒一轮）也会自己判一次窗口：出窗口时把还在转的「抢占恢复」**改成等 Stopped**（不是就地写「已暂停」），停机指令与「已下发」那一步由巡检补上。

**要不要推「抢占恢复」只看这条事件从哪来**：`kind=keepalive_quiet` 只有窗口到点那一条，它不发通知；其余保活拉起全部走抢占恢复渠道、按 `notify_on_keepalive` 开关推通知。不再按「上一轮是否看到它在跑」区分 —— 那个判断把「手动关机后重新开保活」算成了计划内，用户明明要求它在线、机器却没起来，反而收不到消息。

### 停机模式

`servers.stop_mode` 是用户在实例设置里选的偏好（`StopCharging` 节省停机 / `Stop` 普通停机），所有关机动作统一走 `shift.stop_server_by_pref()`；`servers.stopped_mode` 是阿里云返回的**真实**模式，事件与通知里的「已节省停机 / 已普通停机」按它写。选节省停机时保留 fallback（规格不支持则退化为普通停机），选普通停机不 fallback。

## 安全

| 项 | 做法 |
| --- | --- |
| AccessKey Secret / Token / 密码 | AES-GCM，密钥是 `master.key`（32 字节随机，600 权限） |
| 面板密码 | PBKDF2-SHA256，260k 轮，随机盐 |
| 会话 | HMAC-SHA256 签名票据，含过期时间与 `epoch`；改密码时 epoch 自增，旧票据立即失效 |
| CSRF | 双提交 Cookie：`cdt_mgmt_csrf` 必须在 `X-CDT-CSRF` 头回传 |
| 登录限速 | 内存计数，同 IP 5 分钟 8 次 |
| 敏感字段回显 | 只返回 `*_configured: true` 和打码值，永不回传明文 |

`master.key` 丢失等于所有凭据无法解密，所以 README 里反复强调要跟 db 一起备份。

## 为什么是 Python 不是 Go

交付这台机器上没有 Go 工具链，无法编译验证。Python 能本地把「初始化 → 建机器 → 建组 → 对账 → 结算 → 通知文案」整条链路跑通再交付，风险更可控。运行时是 `uvicorn + SQLite`，单容器无外部依赖，镜像基于 `python:3.13-slim`。

`CDT_DRY_RUN=1` 会在内存里模拟实例状态流转（停止 → 启动中 → 运行），配合 `scripts/smoke_test.py` 可以完整验证换班流程而不碰真实阿里云。
