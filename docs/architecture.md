# 架构说明

一份给自己看的实现笔记：为什么这么拆、状态存在哪、换班怎么保证不重复操作。

## 进程模型

单进程，三个线程：

```
uvicorn (asyncio)
 ├── FastAPI 路由          → 同步端点丢到线程池，不阻塞事件循环
 └── scheduler 线程 (daemon)
       ├─ 每 N 秒（对齐到设置的起始秒位）：engine.reconcile_all()
       ├─ 每分钟：检查日报时间
       └─ 每小时：清理事件与采样
```

没有独立 Worker、没有任务队列。对账是幂等的，重复执行没有副作用，所以不需要租约或分布式锁 —— 一个进程内用 `threading.Lock`（非阻塞）挡住并发即可。

SQLite 用 WAL + 每线程独立连接（`threading.local`）。读写混跑不打架；`busy_timeout=15s` 兜住偶发争用。

## 数据模型

```
servers ──────────── 一台机器 = 一个阿里云账号 + 一个 ECS 实例
   │                  quota_gb / threshold_gb / 运行时快照（流量、状态、IP）
   │
   ├── keepalives ─── 单机保活（server_id 唯一）
   │
   └── shift_members ─┐
                      ├── shift_groups ── 联合换班组
                      │      anchor_at：轮换周期的时间原点
                      └── position / hours：顺序与时长

shift_runs ──────── 每个「班次」的执行状态
                      slot = 该班次的开始时间戳（Unix 秒）
                      phase = pending | switching | settled | failover | breaker | error

flags ───────────── 一次性标记（通知去重、恢复待确认）
events ──────────── 事件流，给人看的
traffic_samples ─── 流量采样，给图表用
```

关键设计：**`slot` 用「班次开始时间戳」而非「日期 + AM/PM」**。

这样无论是 2 台各 12 小时、3 台各 8 小时，还是 10h + 14h，都能天然得到唯一且稳定的 slot key。改成员或改时长时重置 `anchor_at`，slot 自然翻新，不会沿用旧标记。

## 轮换算法

```python
total  = Σ(member.hours) * 3600
elapsed = max(0, now - anchor)
cycle  = elapsed // total          # 第几个周期
offset = elapsed % total           # 周期内偏移
逐成员累加，第一个满足 offset < Σhours 的就是当班
```

O(n) 且无状态。`anchor_at` 是唯一需要持久化的东西 —— 手动换班就是改它。

手动换班为什么是「平移 anchor」而不是「记一个强制下次当班」？因为后者会引入一个额外的状态机分支（要判断什么时候失效、跟自然轮换怎么合并）。平移 anchor 之后，系统仍然只有一个真相来源（时间 + anchor），逻辑不分叉。

平移量 = `now - 下一个成员在本周期内的累计起点`。等价于「把 now 当成下一班的第 0 秒」。

## 对账流程

`reconcile_group` 一次跑完：

```
1. 算当班 / 待机
2. 并行刷新所有成员的流量与实例状态
3. 当班超阈值？
   ├─ 有没超的成员 → 换人（failover=true），原当班转入待机集合
   ├─ 全都超了     → 熔断：全员 StopCharging，确认后推熔断报告
   ├─ 别人查不到   → 保守维持（不能因为 API 抖动就把机器停掉）
   └─ 关闭了故障转移 → 超限停机兜底
4. 当班没 Running → Start（若该班次已结算过，打上「待恢复」标记）
5. 当班 Running   → 其余全部 StopCharging
6. 全部就绪（当班 Running + 其余 Stopped/StopCharging + 有公网 IP）
     → 同步 DDNS → 推「换班完成 / 临时换班」
7. 未就绪 → 检查是否超过 10 分钟 → 推「换班异常」
```

几个刻意的选择：

- **DDNS 必须先于通知**。通知文案里会回显 `☁️ DDNS：✅ 已同步`，先发通知再同步会撒谎。
- **只在关键时刻查 Cloudflare**。巡检（`dns.reconcile`）只比本地 `last_ip`，一个请求都不发；手动开机、单机保活拉起、换班首次结算传 `verify=True`，先读 CF 上的实际记录，一致就跳过 PUT。`dns_records.last_at` 的语义是「上次真正改写记录的时间」，核对发现没变时不刷新，界面上不会出现假的「刚刚」。
- **待机没确认停机就不算结算**。只下发了 Stop 指令不算，得看到 `Stopped` 才算 ready，否则会误报「换班完成」。
- **别人的状态查不到时不动手**。宁可这轮什么都不做，也不要基于空数据把实例停掉。
- **超限兜底与熔断分开**。熔断是「都没得选」，超限停机是「换不了但还在跑」；两者的通知文案不同，用户要知道是哪一种。

## 事件标题规范

事件标题统一由 `messages.ev(结论, 对象)` 拼：**结论在前，对象进末尾的括号**，与通知标题
`CDT {结论}报告（{范围}：{对象}）` 同构。结论里不重复对象名，也不再用「对象：结论」或
「对象 结论」的写法 —— 别名长短不一时，两种写法会让整列文字对不齐。

| 对象 | 写法 | 例子 |
| --- | --- | --- |
| 单台服务器 | 裸别名 | `单机保活抢占恢复（AliYun-CDT）` |
| 整个换班组 | `换班组：组名` | `换班完成（换班组：香港）` |
| 组内当班 | `换班组：组名，当班 别名` | `当班未就绪（换班组：香港，当班 A）` |
| 组内普通成员 | `换班组：组名，成员 别名` | `状态读取异常（换班组：香港，成员 B）` |
| DNS 记录 / 系统 | 域名 / `系统` | `DNS 记录已更新（a.example.com）`、`配置已更新（系统）` |

几个约束：

- **括号只有一层**。原因写进结论（`当班未就绪，故障转移（换班组：香港）`），不套第二个括号；
  结论里**最多一个逗号**（原因，结果），三段以上就该拆到概览里。
- **服务器不加类型前缀**，事件列表里九成是机器；换班组一律带前缀，避免与同名实例混淆。
- **结论用词固定**：单机保活分两条渠道，各说各的 —— 窗口到点开/关走
  `单机保活窗口暂停 / 单机保活窗口恢复`，其余拉起（掉线被抢占、手动关机后重新开保活、
  刚加进保活）走 `单机保活抢占恢复`；流量超限暂停仍叫 `单机保活暂停`。
  读取系列只有「状态读取异常 / 状态读取已恢复」两句，具体归属交给括号里的对象。
- **进行中用「X 中」，完成用「已 X」**：`换班进行中 → 换班完成`、`当班自动拉起中 → 当班已恢复运行`、
  `单机保活抢占恢复中 → 单机保活抢占恢复`、`单机保活窗口恢复中 → 单机保活窗口恢复`。
  同一个动作全程只有一个名字，收尾只换时态。
- **不加修饰副词**：`已节省停机` 不写 `已强制节省停机`，`当班未就绪` 不写 `疑被抢占` ——
  判断依据放详情里，标题只留事实。

## 事件三要素

一条事件要能被「扫一眼」和「点开看」两种读法都读懂，三段各管一件事：

| 位置 | 写什么 | 反例 |
| --- | --- | --- |
| 标题 | 结论 + 对象；进行中写 `X 中`，收尾换成 `已 X` | 收尾了还写「拉起完成」 |
| 概览（detail） | **进行中**只写「在等什么」：`等待停机到位（节省停机）`；**完成**只写结果，最多补一段原因，用「 / 」分隔：`已停止（节省停机） / 已用 199.00 GB` | 只写「已下发停机指令」——指令下发≠做到；或者写「A → B」这种看不懂的状态迁移 |
| 详情（progress） | 完整过程 + 结果：为什么做、下发什么、确认到什么状态、DDNS、通知 | 只有第一步，后面什么都没有 |

**凡是要等外部状态的动作，事件一律先 running，等确认到位才收尾**：手动开关机、
单机保活拉起 / 窗口暂停、超限停机、换班结算都走这条路（`pending_status` + `pending_kind`，
由确认器每 5 秒轮询）。只有「指令下发成功」这一件事可写的，不许直接标完成。

## 幂等与去重

每次要发通知前，先查 `flags`：

| 标记 | 作用 |
| --- | --- |
| `notify:{group}:{slot}:settled` | 同一个班次只推一次换班报告 |
| `notify:{group}:{slot}:failover` | 同一个班次只推一次临时换班报告（与上面分开，否则「先结算后又转移」会被吞掉） |
| `breaker:{group}:{slot}` | 熔断只报一次 |
| `limit_stop:{group}:{slot}` | 超限停机只报一次 |
| `timeout:{group}:{slot}` | 换班异常只报一次 |
| `recovery:{group}:{slot}` | 待确认的抢占恢复 |
| `start_err` / `stop_err` / `member_err` / `keepalive_err` | 同类失败只记一条事件，恢复后自动解除，避免每分钟刷屏 |
| `keepalive_rest:{server_id}` | 已记过「单机保活窗口暂停」，休止时段内不再重复记 |
| `keepalive_rest_fail:{server_id}` | 休止时段停机失败只记一次，下一轮继续重试但不刷屏 |

标记落库而不是内存，容器重启后不会重复推送。

开关机的去重靠状态判断而不是标记：`status != Running` 才 Start，`status != Stopped` 才 Stop。阿里云那边状态是真相，所以不需要额外记「已经发过启动指令」。处于 `Starting/Stopping` 这类过渡态时不下发新指令，只等它落地。

### 故障转移是「粘住」的

一个班次内一旦因流量超限切到替补，本班次剩下的时间就固定在替补上（`shift_runs.failover` + `duty_server_id`）。不这么做的话，每轮对账都会重新按时间推导出原当班、再判定一次超限，结果是每分钟换一次机器、事件刷屏、通知重复。界面上的「当班」高亮也跟着 `run.duty_server_id` 走。

### 保留期

| 表 | 保留 | 原因 |
| --- | --- | --- |
| `events` | 14 天（可配） | 只是给人看的流水 |
| `flags` | 90 天起 | 里面混着「已让位」「已熔断」这类长期状态，不能跟事件一起删 |
| `shift_runs` | 30 天 | 抢占恢复要靠上一轮 `phase` 判断，班次最长可到 7 天，删早了会重复推「换班完成」 |
| `traffic_samples` | 7 天 | 画曲线用 |

## 单机保活与换班的互斥

同一台机器如果同时挂在两个模块下，会互相拉扯：保活看到 Stopped 就拉起来，换班看到不该它当班就停掉，来回震荡。

处理方式：`reconcile_all` 先算出「所有进组的 server_id」，保活对账时跳过这些机器，并记一条一次性警告。**让位给换班**，因为换班的约束更强（同一时刻只能一台在线）。

### 运行窗口（单机保活）

`keepalives` 上有两组可选字段，都为空表示不限（等于没有这个功能）：

| 字段 | 约束 | 判定 |
| --- | --- | --- |
| `start_time` / `end_time` | 同一天内，`end > start`，不跨零点；`end=00:00` 表示到 24:00（与联合换班同义） | `start ≤ 现在 < end` |
| `start_day` / `end_day` | 同一个月内，`1 ≤ start ≤ end ≤ 31`，不跨月 | 按当月天数截断后比较 |

两项同时填是**交集**。窗口外：主动按实例的停机模式停机，落一条「单机保活窗口暂停」——**下发指令之后事件仍是进行中**，要等确认器看到 `Stopped` 才收尾（概览写「已暂停（节省停机）」），全程不发通知；回到窗口内：落一条「单机保活窗口恢复中」并在同一轮下发开机，那条事件挂 `pending_kind=keepalive` 等确认，但 `kind=keepalive_quiet`，确认器据此不发「抢占恢复」。

确认器（5 秒一轮）也会自己判一次窗口：出窗口时把还在转的「抢占恢复」**改成等 Stopped**（不是就地写「已暂停」），停机指令与「已下发」那一步由巡检补上。

**要不要推「抢占恢复」只看这条事件从哪来**：`kind=keepalive_quiet` 只有窗口到点那一条，它不发通知；其余保活拉起全部走抢占恢复渠道、按 `notify_on_keepalive` 开关推通知。不再按「上一轮是否看到它在跑」区分 —— 那个判断把「手动关机后重新开保活」算成了计划内，用户明明要求它在线、机器却没起来，反而收不到消息。

### 停机模式

`servers.stop_mode` 是用户在实例设置里选的偏好（`StopCharging` 节省停机 / `Stop` 普通停机），所有关机动作统一走 `shift.stop_server_by_pref()`；`servers.stopped_mode` 是阿里云返回的**真实**模式，事件与通知里的「已节省停机 / 已普通停机」按它写。选节省停机时保留 fallback（规格不支持则退化为普通停机），选普通停机不 fallback。

## 安全

| 项 | 做法 |
| --- | --- |
| AccessKey Secret / Token / 密码 | AES-GCM，密钥是 `master.key`（32 字节随机，600 权限） |
| 面板密码 | PBKDF2-SHA256，260k 轮，随机盐 |
| 会话 | HMAC-SHA256 签名票据，含过期时间与 `epoch`；改密码时 epoch 自增，旧票据立即失效 |
| CSRF | 双提交 Cookie：`cdt_mgmt_csrf` 必须在 `X-CDT-CSRF` 头回传 |
| 登录限速 | 内存计数，同 IP 5 分钟 8 次 |
| 敏感字段回显 | 只返回 `*_configured: true` 和打码值，永不回传明文 |

`master.key` 丢失等于所有凭据无法解密，所以 README 里反复强调要跟 db 一起备份。

## 为什么是 Python 不是 Go

交付这台机器上没有 Go 工具链，无法编译验证。Python 能本地把「初始化 → 建机器 → 建组 → 对账 → 结算 → 通知文案」整条链路跑通再交付，风险更可控。运行时是 `uvicorn + SQLite`，单容器无外部依赖，镜像基于 `python:3.13-slim`。

`CDT_DRY_RUN=1` 会在内存里模拟实例状态流转（停止 → 启动中 → 运行），配合 `scripts/smoke_test.py` 可以完整验证换班流程而不碰真实阿里云。
